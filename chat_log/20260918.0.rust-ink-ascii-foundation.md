# Session: rust-ink-ascii-foundation

## Goal
Explore extracting ascii-renderer's reusable art generation and plugin system into a pure library with a separate high-performance terminal renderer, analogous to React and react-dom or a Rust Ink.js foundation. Performance attribution must make bottlenecks easy to locate.

## Current State
No code was changed. The repository is currently binary-only: Cargo.toml declares two binaries using src/main.rs and has no src/lib.rs. The reusable boundary is present conceptually as explicit ModeFrame inputs into a mutable Grid, but registry, app configuration, profiling, drawing types, terminal colors, and terminal presentation remain coupled in one crate.

## Problem/Context
The desired system needs reusable ASCII generation, a plugin/component API, and a separately mounted terminal runtime. The terminal runtime must support very high frame throughput and expose measurable stage costs. Ratatui is currently used inside the retained animation encoder; its per-frame buffer adaptation and diff work are possible costs, especially for large animated art grids.

The existing frame pipeline is:
CLI/app inputs -> blank/reused Grid -> Mode::render -> Grid -> ANSI encoding or retained Ratatui diff -> playback relay -> terminal.

The repo already profiles generation, encoding, presentation, encoder conversion, diff/emission, bytes, changed cells, skipped cells, invisible changes, runs, and full repaints. Diff scan and ANSI emission currently share one timing field. Existing historical measurements in perf/results/18_split_probe.md report encoder time at 366x199 moving from 1,904 us to 591 us after adapted-cell caching.

## Solution/Approach
Treat the pure library boundary as resolved frame inputs -> caller-owned Grid. Treat terminal mounting as Grid -> retained terminal state -> encoded updates -> transport. Keep plugin registration host-populated rather than tied to the generated built-in global registry. Resolve CLI arguments, environment variables, persisted preferences, and live controls before calling the pure library.

A possible division is:
- art foundation: Cell/Grid/Rect, colors, palettes, drawing primitives, composition, Mode/ModeFrame/Param, host-populated registry
- art plugins: Mode implementations
- terminal adapter: cell conversion, retained presentation state, update selection, ANSI encoding, terminal lifecycle
- application: CLI, demo browser, controls, persistence, morph playback, plugin selection

Performance reports should independently measure component/layout work, art generation, cell adaptation, diff scanning, encoding, transport, and external terminal behavior. Reproducibility inputs include seed, dimensions, parameters, time sequence, palette, build identity, and frame work counters.

## Key Insights
- Mode and ModeFrame already form the smallest shared plugin shell.
- Two inspected modes share the frame contract but implement parameter decoding, cache ownership, geometry, rasterization, clearing, and profiling differently.
- src/modes/_30_illuminarium.rs is 1,353 lines with 10 knobs. It caches a full background plus specialized static element data keyed by dimensions, seed, palette, and all parameters. It paints eight measured layers and uses pp primitives plus local helpers.
- src/modes/_59_gothic_trace.rs is 798 lines with 13 knobs. It caches Vec<Stroke> geometry keyed by dimensions, seed, and eight geometry knobs. Five animation-only knobs remain outside the key. It clears the grid and locally rasterizes visible path intervals. It exposes one measured drawing layer.
- Both use thread-local caches and import opts::param_f32, coupling pure art code to app configuration.
- Both use crossterm::style::Color through Cell, coupling the shared drawing representation to a terminal library.
- IterateFrameRenderer already owns a reusable Grid and deterministic RNG reset behavior.
- AnsiFrameEncoder already owns retained terminal presentation state and writes into a caller-owned byte buffer.
- Animation currently regenerates a frame from seed and time; general simulation state does not persist between frames, though file-local static geometry caches do persist per thread.
- Ratatui's role is limited to adapted retained buffers, diff_iter, wide-character behavior, and backend ANSI drawing. Art generation does not depend on Ratatui.
- A current Rust Ink-like project called rnk exists, but no adoption decision was requested or made.

## Open Questions
- Should components be only Mode-sized frame generators, or should the foundation include a compositional component tree and layout/state model?
- Does the plugin system need dynamic loading, static registration across crates, or only host-populated trait objects?
- Should cached geometry belong to long-lived plugin instances rather than thread-local globals?
- Which renderer workload is primary: mostly unchanged UI cells, high-churn animation, or both?
- Is terminal output the only initial mount target, or should plain text, image, web, and test mounts shape the core API?
- Should profiling be always-on low-cost counters or feature-gated detailed instrumentation?
